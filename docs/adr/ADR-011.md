# ADR-011: PostgreSQL + pgvector for knowledge persistence

## Status

Accepted for Phase 4.

## Context

Phase 4 needs durable documents, chunks, 384-dimensional local embeddings, metadata filters,
retrieval-run audit records, and repeatable incremental indexing. The current platform already
operates PostgreSQL and uses Alembic and async SQLAlchemy. The evaluated corpus is bounded: 13
documents, 2,149 parsed rows, and 2,146 unique stable chunk IDs.

## Options considered

| Option | Strengths | Costs / risks | Decision |
|---|---|---|---|
| Chroma | Simple local development and embedded mode | Separate persistence lifecycle; weaker fit for transactional metadata and audit joins | Rejected |
| Qdrant | Strong vector search, payload filters, and production ANN capabilities | Adds another stateful service and backup/operations surface before corpus scale requires it | Deferred |
| PostgreSQL + pgvector | Transactional document/chunk/audit writes, existing operational stack, SQL metadata filters, future HNSW/IVFFlat support | Python BM25 remains separate; large-scale vector workloads may eventually need a dedicated service | Selected |

## Decision

Use PostgreSQL 16 with the `vector` extension as the canonical knowledge store. Alembic owns
`knowledge_documents`, `knowledge_chunks`, and `retrieval_runs`; embeddings are `VECTOR(384)`.
The immutable `index-v1.json` artifact is the reproducible bootstrap and evaluation input. At the
current size the service loads this bounded artifact and computes exact dense similarity plus BM25
in process, while the same vectors and metadata are transactionally persisted in pgvector. This
avoids an approximate-index confound in the frozen evaluation and keeps retrieval deterministic.

The Compose image is built locally from the official `postgres:16-alpine` base and pgvector 0.8.1
source. The release tarball SHA-256 is pinned and verified; build tools remain in a discarded
builder stage.

Revisit Qdrant or pgvector HNSW when measured corpus size or concurrency makes exact retrieval the
bottleneck. The migration trigger is evidence, not anticipation: sustained p95 above the service
SLO, memory pressure, or corpus growth beyond a size validated by load testing.

## Consequences

- A document hash change replaces only that document and its chunks in one transaction.
- An unchanged hash is skipped; identical repeated stable chunk IDs collapse once, while an ID
  carrying different content is rejected.
- Removed documents are deleted through the document foreign-key cascade.
- Embedding model, dimension, and normalization are versioned in the artifact.
- Knowledge failure is isolated from telemetry ingestion and Phase 3 diagnosis.
