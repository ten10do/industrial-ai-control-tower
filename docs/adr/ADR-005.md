# ADR-005: Redis Role

## Status

Accepted

## Context

The platform needs fast access to transient state, caching, and lightweight messaging without burdening PostgreSQL.

## Decision

Use Redis for caching, session state, rate limiting, and lightweight task queues.

## Alternatives

- **Memcached**: Simpler, but lacks data structures and persistence options.
- **PostgreSQL for everything**: Avoids an extra dependency, but increases load on the primary database and complicates TTL and pub/sub patterns.
- **Kafka**: Powerful for event streaming, but overkill for Phase 0 and adds operational complexity.

## Consequences

- Redis reduces PostgreSQL load for hot data.
- Pub/sub can support future real-time dashboards and agent status updates.
- Redis is not a durable event log; audit events must still be persisted to PostgreSQL or object storage.
